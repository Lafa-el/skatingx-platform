# Pose Landmarker 升级评估（Spike）计划

版本：v1.0 ｜ 日期：2026-10-18 ｜ 状态：草稿，待 M2 固件就绪后启动
背景：旧分析站用 MediaPipe Pose 0.5（legacy Solution API，已被官方弃用）；现行官方方案是 Tasks Vision **Pose Landmarker**。按规范 §9"先平移再升级"，本 spike 独立于 Phase 1 移植轨道。

## 1. 目标

回答一个问题：在"浏览器本地、视频不上传"的红线内，Pose Landmarker 相对 0.5 是否值得切。只做评估与对照，不直接上线。

## 2. 非目标

- 不换框架（不引入 RTMPose/YOLO-Pose 等服务端方案，不转 ONNX）。
- 不改分析算法与业务逻辑；只换姿态估计后端。
- 不动 UI。

## 3. 方法

1. 前置：M2 的去标识化固件集就绪（含固定测试视频与关键点固件，覆盖正常/无人/多人/低帧率/中途取消）。
2. 在隔离分支上接入 Pose Landmarker（WASM，GPU delegate 优先、CPU 兜底），官方三档模型 `pose_landmarker_lite/full/heavy.task` **全部测一遍**（同一套接入代码，只换模型文件，成本几乎相同），**自托管、版本 pin、懒加载**。
3. 同一批固件视频，分别跑 0.5 与 Landmarker，记录逐帧关键点。

## 4. 对照指标

对三档模型各出一份报告，形成"精度 / 速度 / 体积"权衡表：

- **关键点误差**：以 0.5 输出为参照基线（不是真值），计算归一化坐标下的平均欧氏距离；分场景报告（正常/多人/低帧率）。另抽查若干帧做人工目检，确认无系统性错位（如左右颠倒、抖动）。
- **运行时性能**：同设备、同视频的平均帧率（fps）与首帧延迟。
- **体积与加载**：模型文件大小、懒加载后对首屏 bundle 的增量（目标：零首屏增量）。
- **失败模式**：无人帧、多人帧、低帧率输入的行为是否与 0.5 基线一致（M1 quirks 基线）。

## 5. 验收与切换

- 选型原则：**精度优先，默认 heavy**。三档全测，heavy 为默认选项；仅当 heavy 在目标真机上达不到性能门槛（持续分析帧率、内存占用、模型加载耗时——阈值由用户在评审对照报告时批准）时，才降档到 full/lite。降档是性能不达标时的让步，不是为省体积的默认动作。
- 若 heavy（精度上限）都超不过 0.5，则整个 Landmarker 家族直接判负，不再试其他方案。
- 达标 → 独立 PR 切换选定的模型档（feature flag 或版本开关），灰度验证后全量；0.5 实现保留一个版本，Vercel 可即时回滚。
- 不达标 → 结论归档（记录差距与复测条件），继续用 0.5，不阻塞 Phase 1 其他里程碑。
- 体积备注：模型自托管 + 懒加载，赛前一晚在线打开一次即完成预加载并缓存，之后离线可用；体积代价是一次性的，不影响首屏。

## 6. 红线

- 视频不上传；无 secret、无生产数据进提交；测试只用去标识化固件。
- 与 Phase 1 移植轨道的接口：只读 M2 固件与类型，不互相阻塞；切换 PR 不得搭车改业务逻辑。
