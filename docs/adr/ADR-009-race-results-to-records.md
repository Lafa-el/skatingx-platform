## 1. 冲突

ADR-001 为 Phase 0 规定：

- D4 的非目标列表包含「automatic PB sync」。
- D5 写明「Results never auto-write to PB records in Phase 0. "Super 1500m" is not in `DEFAULT_TRAINING_DISTANCES`; mapping is deferred.」

本 ADR **取代**这两条中关于「成绩不写纪录」和「Super 1500m 映射推迟」的部分：已确认的本人成绩由系统自动同步进训练纪录，Super 1500m 归入 1500m。

ADR-001 其余内容不变：成绩仍然录入即 pending，确认仍是手动动作，比赛日自己的子树、规则和离线排队不动。D5 的精神也保留：只有用户确认过的成绩才进入纪录，日期不猜。

## 2. 决定

### 2.1 触发点

一条成绩进入纪录，当且仅当：

- `isConfirmed(result)`，即 `result.verification === "verified"`；
- `result.status === "finished"`，且 `result.timeSeconds` 是 `0 < t <= 1800` 的有限数。

录入（`createRaceResult`）和编辑（`updateRaceResult`）写出的都是 pending，不进纪录。DNS / DNF / DQ 没有时间，不同步。

### 2.2 同步对象

只同步**本运动员**的成绩：

- 每个赛事的名单里取「本人行」：`isSelf === true`，多条时按 `rosterId` 排序取第一条，与总结页和今天页的选法一致。
- 本人行的 `athleteRefId` 必须等于**当前运动员**（`useActiveAthlete().athleteId`）。成绩写进当前运动员的纪录。
- 被关注者没有 `athleteRefId`，不同步。本人行 `athleteRefId` 为 `null`，不同步。

对账只动当前运动员的纪录文档。因此本人行改指向另一位运动员后，那位运动员成为当前运动员时，会把旧条目当作「已无来源」清理掉，不留孤儿。

### 2.3 距离映射

映射依据是赛程行 `distanceId`，写成一张查表，不做字符串猜测：

| 赛程 `distanceId` | 纪录 `distanceId` |
|---|---|
| `333m` / `500m` / `777m` / `1000m` / `1500m` | 同值 |
| `super_1500m` | `1500m`，条目 `note` 保留项目名 |
| 其他任何值 | 不同步 |

owner 已确认 Super 1500m 归入 1500m（2026-10-30）。不新建 `super_1500m` 纪录文档：纪录页只遍历 `DEFAULT_TRAINING_DISTANCES`，多出来的文档看不到。

### 2.4 条目内容与幂等

- 条目 id：`race_{eventId}_{raceId}`。`eventId`、`raceId` 都是 `isValidRaceDayId` 允许的小写字母、数字和连字符，不含 `_`，可无歧义拆回。不用 `rosterId`：名单行删了重建，`rosterId` 会变，同一场比赛会重复。
- `source: "race"`，`timeSeconds` 取 `result.timeSeconds`（两边同为秒，不换算）。
- `date`：取 `race.day`；为 `null` 时仅当事件只有一个合法日期才取它；否则不同步。不猜。
- `note`：`{event.name} · {race.label}`。`race.label` 是赛程里的项目名（Super 1500m 的模板标签就是「Super 1500m」）。
- upsert：id 已存在且内容一致则不动；不一致则更新 `timeSeconds`、`date`、`note`、`updatedAt`，保留 `createdAt`；不存在则追加。
- 同步只拥有 id 为 `race_{eventId}_{raceId}` 形状的条目；手填的（`time_…`）、迁移来的（`legacy-time-…`）、以及任何形状不符的条目，**原样保留，不读不改不删**。

### 2.5 对账，不挂确认点击

同步是一个幂等的对账：由比赛日数据算出「应有条目集合」，与纪录里已有的 `race_` 条目比对，差多少补多少。

- 运行位置：`RaceDayLayout` 里的一个 hook，订阅所有赛事的事件、名单、赛程、成绩。订阅的数据变化（包括本地离线写入引起的变化、级联删除引起的变化）后，防抖，再对账一次；浏览器恢复在线时再对账一次。
- 不在确认按钮里挂写操作：比赛现场常离线，事务不排队（`training-plan.ts` · `setPlanFocus` 的注释），挂在点击里会让确认失败；同时覆盖不了删赛程、删名单、删赛事的级联删除。
- 写入：每个有变化的纪录文档开一个事务，事务内重读，以事务内的数组为准再算一次，写回。读不到或写失败只记日志并重试，不影响比赛日的任何操作。
- 在途标记防重入：对账进行中又来变化，结束后再跑一次。
- 对账只读比赛日数据和纪录文档，**不写任何比赛日文档**。
- 只在 `isRaceDayEnabled()` 为真、用户进入比赛日模块时运行。

### 2.6 删除与退回传导

纪录里的 `race_` 条目是成绩的**派生数据**，来源不在了或不再可信，它就移除：

| 来源的变化 | 条目 |
|---|---|
| 成绩被删 | 移除 |
| 成绩退回待确认，或被编辑（编辑必然回到待确认） | 移除；重新确认后按新值加回，始终一条 |
| 赛程行被删（连带删该场成绩） | 移除 |
| 名单行被删（连带删该人成绩） | 移除 |
| 赛事被删（递归删子集合） | 移除 |
| 赛程行的项目改成映射表以外 | 移除 |
| 本人行不再指向当前运动员 | 移除 |

### 2.7 读不全保护

宁可多留一条旧条目，不可误删用户数据。「移除」只在**确定来源已不存在**时发生：

- 事件列表读失败、未就绪或含有无法解析的文档：整次不做**任何移除**（只增改）。
- 某个赛事的名单、赛程、成绩任何一份未就绪、读失败或含无法解析的文档：该赛事的条目不移除。
- **只来自本地缓存的列表不算读全。** 缓存里可能只有本机写过的几条文档，缺的并不等于已删除。订阅带 `includeMetadataChanges`，列表的 `snapshot.metadata.fromCache` 为真时一律按「未读全」处理，服务器应答后（元数据变化再触发一次）才允许移除。离线时不运行对账，恢复在线后再运行。
- 无法解析的事件文档的 id，其条目不移除。
- 纪录文档的 `entries` 不是数组：跳过该文档。
- 不识别的条目一律原样保留（2.4 的最后一条）。

### 2.8 纪录页配合

`race_` 开头的条目，在纪录页把「编辑」「删除」换成一行说明：「由比赛成绩同步而来，随成绩走」。原因：对账会把手改的值改回、把手删的条目补回。这只改列表行的按钮，**不碰** `getBestTime`、`getLatestTime`、`useTrainingRecords` 的取值。个人最好仍是纪录页对 `entries` 取最小值，同步只负责增改删条目。

用户在纪录页手填一条来源选「比赛」的条目，id 仍是 `time_…`，仍可编辑、删除，不受同步影响。

### 2.9 规则与数据

- **不改 `firestore.rules`。** `training/main/records/{distanceId}` 落在 `match /athletes/{athleteId}/{a}/{b}/{c}/{d}`，对属主开放读写（只排除 `equipment/main/records`）。
- 不新增字段、不新增集合；条目用现有 `TimeEntry` 字段，`TimeEntrySource` 已含 `"race"`。
- 显示位数不同：比赛日按需显示 3 位小数，纪录页固定 2 位。比较大小用完整数值，不受影响。

## 3. 备选与代价

| 备选 | 为什么不选 |
|---|---|
| 确认时在同一个事务里同时写成绩和纪录 | 事务离线不排队，会让比赛现场确认在断网时失败，与 ADR-001 D7 冲突；覆盖不了级联删除 |
| 云函数监听成绩文档 | 仓库没有 Functions，不在标准栈里 |
| 成绩编辑时保留旧的已确认值，直到重新确认 | 纪录里会短暂留着用户刚改过、因此可疑的数字 |
| 纪录生成后归用户所有，不随来源删除 | 来源不可追溯，错的 PB 无法自愈 |
| 新增 `super_1500m` 距离 | 纪录页看不到；要改 `DEFAULT_TRAINING_DISTANCES` 和建档行为，超出范围 |
| 同步名单里所有人的成绩 | 被关注者没有纪录文档；他们的成绩会污染本运动员的 PB |

代价：同步最终一致，不是瞬时。离线确认的成绩，要等应用在线且打开过比赛日才会进纪录。进入比赛日后，每个赛事多 3 个监听，赛事数量有限（ADR-001 D6：每个赛事不到约 50 文档）。

## 4. 已知边界

- 赛程行 `day` 为 `null` 且事件有多个日期时，成绩不同步。比赛日模板创建的赛程行 `day` 都是 `null`，多日赛事需要用户在赛程页给每场比赛选日期后才会同步。这是「日期不猜」的直接后果。
- 对账只在用户进入比赛日模块时运行；只在比赛日之外改了数据的情况不存在（比赛日数据只能在模块里改）。
- 纪录页里的手填条目与对账并发：手填路径仍是非事务读改写（`addTimeEntry`），对账用事务且只动 `race_` 条目；极端并发下手填可能覆盖对账结果，下一次对账会补回。该债务不在本 ADR 范围内。

## 5. 回滚

- **代码：** revert 本 PR。对账停止，纪录页的 `race_` 按钮恢复为可编辑。
- **已写入的数据：** `race_` 条目是惰性数据，留在纪录里不影响 PB 计算（仍是取最小值）。需要清理时，另立任务：先只读审计（列出各距离文档里 `race_` 开头条目的 id 和数量，不打印时间之外的内容），再用默认 dry-run 的受控脚本移除。本 PR 不含清理脚本。
- **关闭开关：** `VITE_FEATURE_RACE_DAY` 关闭后，模块不加载，对账不运行；已写入的条目不变。
- 上线前，若要核对生产里是否已有以 `race_` 开头的条目 id，必须先做只读审计。

## 6. 验证

- 纯函数单测（`packages/skating-domain/src/race-record-sync.test.ts`）：触发点、映射、日期规则、只同步本运动员、幂等、编辑回 pending 移除再加回、各种删除传导、读不全不删、名单重建不重复、不识别条目原样保留。
- 对账函数测试（`packages/firebase-client/src/firestore/race-record-sync.test.ts`）：事务内增改删、无变化不写、`entries` 非数组跳过、文档不存在时建档。
- 订阅循环测试：未读全不删、缓存列表不删、事件被删后释放监听并允许移除、离线等待、防重入、失败重试、卸载释放。
- hook 与布局测试：启动、换运动员重启、卸载释放；`RaceDayLayout` 挂载了它。
- 纪录页组件测试：`race_` 条目无编辑 / 删除按钮、有说明行；手填条目不受影响；个人最好仍是全部条目的最小值。
- 截图证据：`docs/adr/ADR-009-evidence/`（同步前后的纪录页，真实页面组件加用本 ADR 的纯函数算出的数据）。
- 门禁：`lint`、`typecheck`、`test -- --run`、`build`、`test:rules`。

## 7. 实现中的两处顺带说明

- `isValidRaceDayId` 挪到独立的 `race-day-id.ts`（`race-day.ts` 原样再导出，公开路径不变），条目 id 的辅助函数放在 `race-record-entry-id.ts`。原因：纪录页要用 `isRaceSyncedEntryId`，若它依赖 `race-day.ts`，打包器会把比赛日的整块代码拉进主包；拆开后主包只增加约 0.7 kB。
- `RaceDayList` 增加可选字段 `fromCache`，四个订阅函数增加可选参数 `includeMetadataChanges`。现有页面不传，行为不变。
